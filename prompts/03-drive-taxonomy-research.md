# 03 · Research-backed folder taxonomy

**Use when:** a shared Drive has grown without rules and a new structure needs to survive yearly turnover.

**Agent setup:** web search and fetch (official docs only), read access to the current folder inventory, a document tool for the output.

---

```text
Propose a folder structure and naming convention for a shared Google Drive used
by about {{N_MEMBERS}} people, with members rotating every year and a few
permanent coordinators.

Step 1 · Research. Compare at least 8 folder-organization methods
(for example Johnny.Decimal, PARA, chronological, by document type, by owner)
and at least 5 naming conventions (ISO 8601 dates, versioning, etc.).
Use primary sources and link them. One line per method: what it optimizes,
what it breaks.

Step 2 · Fit. From the inventory and the brief, list the project's real
characteristics (turnover, audit needs, image-consent rules, grant reporting...).
For each one, say which method it favors or rules out.

Step 3 · Ask me one question: which matters most, scalability, ease of use
or search? Wait for my answer before Step 4.

Step 4 · Proposal.
- Folder tree with numbered ranges and reserved ranges for growth.
- Naming table by document type, with 3 examples each.
- Permission matrix by role (access follows the role, not the person).
- Check the platform's real permission model in the official docs before
  proposing restricted subfolders. Say what you verified and where.
- A 45-minute launch meeting script and a one-page "where do I save this?" tree.
- A migration plan in phases, each with a rollback.

Rules: no real names, links or IDs in the output. Mark every claim about the
platform as "verified" (with source) or "assumption".
```

---

**Why it is built this way**
- Research before proposal, and a forced stop for one human decision (Step 3), keeps the agent from optimizing the wrong thing.
- "Verified vs assumption" made the agent check how Drive permission inheritance really works, which changed the proposed structure.
